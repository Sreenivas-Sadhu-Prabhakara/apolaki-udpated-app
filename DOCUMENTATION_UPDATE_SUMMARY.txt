KEY ARCHITECTURAL CHANGES
================================================================================

SEPARATE DEPLOYABLES:
  Frontend (frontend/) - Standalone, deploys independently
  Backend (middleware/) - Standalone, deploys independently
  Data Layer - External services, configuration-driven

CONFIGMANAGER PATTERN:
  ✓ All config loaded at startup
  ✓ Priority: Env vars → Vault → Config files → Defaults
  ✓ Fail-fast if required settings missing
  ✓ NO hardcoded credentials, endpoints, or secrets
  ✓ Same code, different config = dev/staging/prod

NETLIFY COMBINED DEPLOYMENT:
  ✓ Single netlify.toml orchestrates both frontend + backend
  ✓ Frontend: Static site (frontend/dist)
  ✓ Backend: Netlify Functions (middleware/functions)
  ✓ All secrets in Netlify Dashboard → Build & Deploy → Environment

ZERO HARDCODING POLICY:
  ❌ NEVER: const DB_HOST = 'localhost'
  ❌ NEVER: process.env.DB_HOST || 'localhost'
  ✅ ALWAYS: const config = await ConfigManager.load()

================================================================================
GOVERNANCE IMPACT
================================================================================

NEW CONSTITUTIONAL LAWS:
  1. Code must be independently deployable (frontend separate from backend)
  2. ALL configuration must use ConfigManager (MANDATORY)
  3. NO configuration can be hardcoded (ABSOLUTE PROHIBITION)
  4. Configuration priority is fixed (Env vars → Vault → Files → Defaults)
  5. Startup must validate all required settings (FAIL-FAST)
  6. Secrets must NEVER be in version control (STRICT ENFORCEMENT)
  7. Same image runs in all environments with different config (IMMUTABLE)

AGENT RULES UPDATED:
  ✓ Agents must use ConfigManager for all external config
  ✓ Agents must respect separate deployable boundaries
  ✓ Agents must document environment variables
  ✓ Agents must validate config at startup
  ✓ Agents must never hardcode credentials

SECURITY IMPROVEMENTS:
  ✓ Secrets stored in vault/platform variables only
  ✓ Config errors caught at startup (fail-fast)
  ✓ Zero environment-specific bugs (same code everywhere)
  ✓ Secrets can rotate without code changes
  ✓ Easy to audit what config is required

================================================================================
CONFIGURATION HIERARCHY
================================================================================

Priority 1: ENVIRONMENT VARIABLES (Highest priority)
           Example: NETLIFY_CONTEXT environment vars

Priority 2: VAULT SERVICES (AWS Secrets Manager, HashiCorp Vault)
           Example: Sensitive secrets retrieved at startup

Priority 3: CONFIG FILES (Development only, Git-excluded)
           Example: .env.local

Priority 4: HARD DEFAULTS (Only for non-sensitive, non-required)
           Example: Timeouts, pagination defaults

Priority 5: NONE FOR REQUIRED SETTINGS ← Fail loudly if missing

================================================================================
WHAT CANNOT BE HARDCODED
================================================================================

Database Connection:        DATABASE_HOST, DATABASE_PORT, DATABASE_USER, PASSWORD
Cache Connection:           REDIS_HOST, REDIS_PORT, REDIS_PASSWORD
Security:                   JWT_SECRET, API_KEYS, SIGNING_KEYS
API Endpoints:              THIRD_PARTY_API_URL, SERVICE_URLS
Credentials:                Any username, password, token
Feature Flags:              Should come from database or feature flag service

WHAT CAN BE HARDCODED (with env var override):

API Port:                   Default 3000, can be overridden
Timeouts:                   Default 30s, can be overridden
Pagination Limits:          Default 20, max 100
Cache TTL:                  Default 3600s, can be overridden
Log Levels:                 Default 'info', can be overridden

DEPLOYMENT WORKFLOW EXAMPLES
================================================================================

DEVELOPMENT:
  $ npm run dev
  → Loads .env.local (Git-ignored)
  → ConfigManager validates local config
  → Services start with local database
  → Changes auto-reload (Vite for frontend, nodemon for backend)

STAGING:
  $ git push origin staging
  → Netlify triggered
  → npm run build:all
  → Frontend built to frontend/dist
  → Backend prepared as functions
  → Netlify injects staging environment vars
  → Services validate config
  → Deploy to staging URL

PRODUCTION:
  $ git push origin main
  → Netlify triggered
  → npm run build:all (same as staging)
  → HUMAN APPROVAL REQUIRED in Netlify dashboard
  → Netlify injects production environment vars (from vault)
  → Services validate config
  → Deploy to production domain

SAME CODE IN ALL ENVIRONMENTS ← Only env vars differ!

================================================================================
CONFIGMANAGER PATTERN
================================================================================

Load Configuration:
  const config = await ConfigManager.load();
  → Checks environment variables
  → Checks vault service (if configured)
  → Checks config files (development only)
  → Validates required settings
  → Throws error if invalid

Inject into Services:
  class AuthService {
    constructor(config, repository) {
      this.jwtSecret = config.security.jwtSecret;  // From ConfigManager
      this.repository = repository;
    }
  }

Startup Pattern:
  try {
    const config = await ConfigManager.load();
    const app = new Application(config);
    await app.start();
  } catch (error) {
    console.error('Fatal configuration error:', error.message);
    process.exit(1);  // Fail fast, don't run with bad config
  }

Netlify Environment Variables:
  Set in: Netlify Dashboard → Site Settings → Build & Deploy → Environment
  Examples:
    DATABASE_HOST=apolaki-db.example.com
    DATABASE_PORT=5432
    DATABASE_USER=app_user
    DATABASE_PASSWORD=[from AWS Secrets Manager]
    JWT_SECRET=[from vault]

MIGRATION GUIDE FOR EXISTING CODE
================================================================================

If you have:
  const config = { host: 'localhost', ... }

Change to:
  const config = await ConfigManager.load();

If you have:
  const host = process.env.DB_HOST || 'localhost';

Change to:
  const host = config.database.host;  // ConfigManager ensures it exists

If you have:
  global.config = { ... };

Change to:
  // Pass config to constructor instead
  class Service {
    constructor(config) {
      this.config = config;
    }
  }

If you have:
  .env file with secrets:

Change to:
  1. Delete .env file
  2. Create .env.example with template
  3. Set actual values in Netlify Dashboard
  4. Use ConfigManager to load at startup

SECURITY IMPROVEMENTS
================================================================================

BEFORE (Hardcoded):
  ❌ Secrets in code or committed .env
  ❌ Same credentials for all environments
  ❌ Env-specific bugs (code differs)
  ❌ Can't rotate secrets without code change
  ❌ Developers exposed to production secrets
  ❌ Container image differs per environment

AFTER (ConfigManager):
  ✅ Secrets in vault/platform variables only
  ✅ Different secrets per environment
  ✅ Identical code everywhere (config is the difference)
  ✅ Can rotate secrets without redeploying code
  ✅ Developers never see production secrets
  ✅ Single container image for all environments
  ✅ Failed startup if required settings missing
  ✅ Audit trail of who set what (in vault/Netlify)

QUESTIONS?
================================================================================

Q: Can I use .env files in development?
A: Yes, .env.local (Git-ignored) works. ConfigManager reads env vars.

Q: What if I forget to set an environment variable?
A: ConfigManager throws error at startup and process exits. Fail-fast.

Q: Can I have different ConfigManagers for different services?
A: Yes, each service can extend ConfigManager for service-specific settings.

Q: How do I rotate secrets?
A: Update in vault or Netlify Dashboard, redeploy. No code change.

Q: Why same code for all environments?
A: Eliminates env-specific bugs. Config is the only difference.

Q: Can feature flags use ConfigManager?
A: No, feature flags change at runtime. Use database or feature flag service.
